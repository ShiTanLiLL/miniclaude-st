# 第 5 课预习 · 没有计划的 Agent，做着做着就偏了

> 上阶段毕业时我们的 Agent 已经能干很多事。这节课上课前，先听老师讲个真实的小故事。

## 一、下节课要解决什么问题？

有一次老师让早期的 Agent 干一件三步小事："读一下配置文件，把超时改成 120 秒，然后告诉我改完的结果"。它读文件读到一半，兴趣来了，跑去"顺手"整理了半个不相关的目录；回过头来改配置时，忘了第一步读到的端口号，又读了一遍；最后汇报的时候，把"还没改"说成了"已改"。三步的活儿，六轮才磨完，中间还闹了个乌龙。

问题出在哪？**它没有工作记忆里的"计划"**。聊天记录里都是命令和输出这种流水账，"我要做哪几步、做到哪一步了"这件事，全靠模型在几十条消息里自己捞。步骤一多，它就开始漂。

下节课的药方说出来特别朴素：**让它先把计划写下来，干活时对着表走**。具体是三件事——一个 `todo_write` 工具（模型提交整份清单）、一个 Harness 侧的清单保管员（负责校验和渲染）、一个督促机制（连续三轮不更新清单就提醒它"看看你的表"）。

## 二、三个课前小知识

- **状态机**：每条待办只有三种状态——`[ ]` 没开始、`[>]` 正在做、`[x]` 做完了。特别是一条铁律：**全局同时只允许一条"正在做"**。这不是抠门，是给模型加的注意力缰绳——强迫它线性推进，不许八面开花。你以后学第 10 课的任务系统时会发现，那边的状态机宽松多了——因为那里管的是"多个任务"，这里管的是"一次专注"。
- **全量替换，不是逐条改**：模型每次调用 todo_write 提交的是**整份清单**，不是"把第 2 条标成完成"这种补丁。为什么？清单总共不过几条，全量提交让模型每次都重新对全局有把握，也省掉了一套复杂的"局部更新"协议。简单，是设计出来的。
- **字符串也可能混进来**：模型偶尔会不按说明书出牌，把清单当字符串交上来。我们会做两层宽容：先按 JSON 解析，不行再按 Python 字面量解析（`ast.literal_eval`），再不行才报错。**对模型的输入保持一点弹性，是 Harness 的日常温柔**。

## 三、课前小任务

想想你自己：你用什么方式管自己的待办？手机清单？便利贴？脑子里？（老师猜是最后一种，然后经常忘。）下节课你会看到，给模型配清单和给自己配清单，最难的都不是"记下来"，而是"记得更新"——所以我们连督促机制都做了。

好，进正课吧。
